# 主控制台探索结算性能（2026-10-21）

针对「一键结算」和「结算完毕」的重复工作做了优化，结算规则不变。

## 实测定位

在本机用无界面 Chrome、真实 localhost PHP 和独立临时账号运行对照。大存档样本由约 4.28 MB 的本地存档只读复制到内存，保留历史、记录表和科技规模，替换当前测试探索牌组。测试数据、会话和备份均落在临时目录；结束后关闭 PHP、清理副本，并校验原存档哈希未变。未加入人工网络延迟。

对照为本次优化前的 Git HEAD 与当前代码，各 3 轮，取中位数。测试包含资源自动结算、仍有手动选择的结算及其收尾。

| 路径 | 点击到下一帧：优化前 → 后 | 前台请求数：前 → 后 | 流程渲染耗时：前 → 后 |
| --- | --- | --- | --- |
| 一键结算，自动效果全部完成 | 290.5 → 265.6 ms | 5 → 2 | 76.1 → 36.8 ms |
| 一键结算，仍有手动选项 | 153.5 → 146.3 ms | 2 → 2 | 36.8 → 36.6 ms |
| 结算完毕 | 337.6 → 309.2 ms | 6 → 3 | 78.9 → 45.0 ms |

规则运算本身约 1 ms，结算预演约 3–4 ms。重复流程渲染是本次测得最大的单项前端开销；存档克隆、比较与合并也占用几十毫秒。独立真实 PHP API 探测中，记录读取、全战役读取、合并保存中位数分别约 27、37、52 ms，均非秒级。

## 改动

- 结算客户端携带当前页面标识。主控制台不再响应自己的保存广播，避免随后重读 dashboard、record 和完整 campaign；其他页面及旧版发送者仍正常触发同步。
- 结算提交阶段更新数据和日期轨，流程区等本轮收尾完成后刷新一次，去掉中间那次重建。
- 折叠的探索卡库与暂移牌堆在第一次展开时构建，之后两区共用同一内容，保留未应用的勾选草稿。五循环隔离节点计数由 232–264 降至 20；该计数不代表整页等待时间的同比降幅。
- 两个结算入口共用缓存有效性检查。已知过期直接读取，未知冲突仍按版本号读取重试；缓存中的记录与其版本号配对。

## 验证和边界

- 552 项相关 Node 测试通过，另有探索牌堆交互脚本通过。
- 浏览器对照逐轮核对资源、数值、牌堆及回执等结果摘要，优化前后一致；没有页面错误或失败弹窗。

## 追加：复用已确认保存的数据，减少整档读取

本页独立保存记录表后，结算上下文原来仍保留旧记录和版本号，因此点击「结算完毕」又下载一次整份战役。现在成功响应到达后，将刚保存的记录副本与服务端返回的版本号一起记入缓存；主控台部分直接复用与当前版本号配对的服务端基线。失败或响应丢失不会推进缓存，账号、会话或档案变化时也不接收旧写入结果。其他模块仍带原版本号提交，任何未知外部修改都由服务端拒绝后重新读取、重试。
